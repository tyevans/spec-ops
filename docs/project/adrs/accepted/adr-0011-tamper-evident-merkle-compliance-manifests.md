# ADR-0011: Tamper-Evident Merkle Tree Compliance Manifests

## Status
Accepted

## Context
Enterprise compliance audits (e.g., SOC2 Type II, ISO 27001 Annex A, HIPAA, FedRAMP) require continuous, unalterable proof of Software Development Life Cycle (SDLC) integrity, traceability, and non-repudiation:
$$\text{PRD} \longrightarrow \text{User Story (Gherkin)} \longrightarrow \text{Task} \longrightarrow \text{Agent Prompt} \longrightarrow \text{Commit SHA} \longrightarrow \text{Test Results} \longrightarrow \text{Human Review}$$

Traditional enterprise compliance regimes suffer from foundational vulnerabilities:
1. **Disparate, Mutable Audit Artifacts**: Audit evidence is typically collected weeks after the fact via manual screenshots, Jira CSV exports, CI pipeline logs, and email threads—all subject to post-hoc tampering, omission, and credential theft.
2. **Autonomous Agent Attribution Deficit**: As autonomous AI coding agents generate, refine, and commit code, auditors reject pull requests lacking provable prompt origin, reproducible preflight test attestations, and dual-custody cryptographic sign-offs.
3. **Traceability Rot**: Disconnected databases cannot prove that a specific commit on `main` was directly authorized by an accepted PRD and verified by automated blackbox acceptance tests without human backdoor tampering.

SpecOps requires a mathematically verifiable, content-addressed compliance manifest that binds the entire SDLC artifact graph into a single top-level cryptographic digest ($O(1)$ verification) while enabling $O(\log N)$ partial inclusion proofs for individual task deliverables.

## Decision
We adopt **RFC 8785 canonical serialization and RFC 6962 power-of-2 binary Merkle trees** as the cryptographic compliance manifest specification for SpecOps (`spec-ops security audit` and `spec-ops audit export`):

### 1. Canonical Serialization (RFC 8785 JCS)
To prevent hash divergence caused by whitespace differences, indentation, key insertion ordering, or platform float formatting:
- All dictionary payloads are serialized strictly using **RFC 8785 JSON Canonicalization Scheme (JCS)**.
- Keys are sorted lexicographically by comparing UTF-16 code units (`key.encode("utf-16-be")`).
- Formatting delimiters are compacted with zero whitespace (`separators=(",", ":")`).
- UTF-8 characters are emitted unescaped (`ensure_ascii=False`) with minimal standard JSON string escaping for quotes, backslashes, and control characters (`\u0000` through `\u001f`).

### 2. Cryptographic Domain-Separated Hashing (RFC 6962)
To prevent second-preimage attacks and leaf/interior node confusion (governed by RFC 6962 §2.1):
- **Leaf Hashing**:
  $$\text{LeafHash} = \text{SHA-256}\left(0\text{x}00 \mathbin{\Vert} \text{JCS}(\text{DeliverableData})\right)$$
- **Interior Node Hashing**:
  $$\text{NodeHash} = \text{SHA-256}\left(0\text{x}01 \mathbin{\Vert} \text{LeftChildHash} \mathbin{\Vert} \text{RightChildHash}\right)$$
- **Empty Tree Root Hash**:
  $$\text{Root}(\emptyset) = \text{SHA-256}\left(\text{""}\right) = \texttt{e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855}$$

### 3. Power-of-2 Binary Tree Calculation Algorithm
For an ordered sequence of $N$ deliverables sorted deterministically by canonical `task_id`:
1. If $N = 0$: Return $\text{Root}(\emptyset)$.
2. If $N = 1$: Return $\text{LeafHash}_0$.
3. If $N > 1$: Let $k$ be the largest power of two strictly smaller than $N$ ($k < N \le 2k$):
   $$k = 2^{\lfloor \log_2(N-1) \rfloor}$$
   Recursively compute:
   $$\text{MTH}(D[0:N]) = \text{SHA-256}\left(0\text{x}01 \mathbin{\Vert} \text{MTH}(D[0:k]) \mathbin{\Vert} \text{MTH}(D[k:N])\right)$$

This construction provides optimal balance, deterministic tree depth $\lceil \log_2 N \rceil$, and standard interoperability with RFC 6962 Certificate Transparency auditors.

### 4. Logarithmic Inclusion Proof Generation & Verification
Auditors can verify individual deliverables without downloading or inspecting the entire repository:
- **Proof Generation**: At each tree split $k$, if target index $m < k$, append sibling $\text{MTH}(D[k:N])$ marked as right; if $m \ge k$, append sibling $\text{MTH}(D[0:k])$ marked as left.
- **Proof Verification**: Starting from $\text{LeafHash}$, iteratively combine sibling hashes according to direction. The resulting hash must match the manifest `root_hash`.

## Consequences

### Positive
- **Automated SOC2 / ISO 27001 Readiness**: Eliminates weeks of manual audit evidence compilation. A single CLI command yields mathematically verifiable proof of full SDLC traceability.
- **Zero Second-Preimage Vulnerabilities**: Explicit domain separation (`0x00` leaf, `0x01` interior node) guarantees immunity to Merkle collision attacks.
- **Efficient Selective Disclosure**: External auditors can inspect a single controversial pull request or feature via an $O(\log N)$ inclusion proof without accessing proprietary code outside the audited slice.
- **Total Tamper Evidentness**: Any modification to a commit SHA, test output, prompt digest, or human signature breaks both leaf and root hashes deterministically.

### Negative
- **Canonical Serialization Overhead**: Requires recursive dictionary sorting and serialization conforming strictly to RFC 8785 prior to leaf hashing (benchmarked at <5ms for typical project repos).
- **Proof Storage**: Storing inclusion proofs in compliance exports incurs small metadata overhead ($\sim 1\text{ KB}$ per deliverable).
